How This Was Built

Overview

This résumé site is intentionally a small, working demonstration of the platform-engineering practices described in the résumé itself: a golden-path static-site deployment on AWS, all infrastructure defined as code, a real CI/CD pipeline with no long-lived secrets, invite-only access control, a live page-aware AI assistant, and a documented AI-assisted build process. The site is not a novelty — the architecture is the point.

Why this matters for the DevEx role: The job description asks for hands-on experience with internal developer platforms, golden paths, IaC, GitHub Actions, and evaluating AI-assisted engineering practices. This project exercises all of those muscles on a real, public artifact.

Architecture

Hosting: S3 + CloudFront (Origin Access Control)

Site files live in a private S3 bucket — no public access is enabled at the bucket level. A CloudFront distribution sits in front using Origin Access Control (OAC), the current AWS-recommended approach (replacing the legacy Origin Access Identity). CloudFront is the only authorized principal that can read objects from the bucket.

This is the textbook "golden path" architecture for static sites on AWS: fast global edge delivery, HTTPS enforced end-to-end, origin kept private, and essentially zero operational overhead at this traffic level.

Caching Strategy

  • HTML files — Cache-Control: no-cache (1-second CloudFront TTL). Updates appear immediately after a CloudFront invalidation.
  • Static assets (CSS, JS, images) — long cache TTL (1 year). These are treated as immutable; change the filename/hash to bust cache.

HTTPS & Custom Domain

HTTP-to-HTTPS redirect is enforced at the CloudFront level. The site runs on its own custom domain, resume.pages-enterprise.com — see Custom Domain below for how that's wired up.

Infrastructure as Code: AWS CDK (TypeScript)

All AWS resources — the S3 bucket, CloudFront distribution, OAC, bucket policy, and cache behaviors — are defined in a single CDK stack (infra/lib/resume-site-stack.ts). No resources were created manually in the console. This means:

  • The infrastructure is reproducible, reviewable, and version-controlled.
  • Drift is detectable via cdk diff.
  • Teardown is a single cdk destroy.

Access Control: Email OTP Gate

The deployed site is invite-only — every page is gated behind email verification, not just visible to anyone with the URL. A CloudFront Function (viewer-request, not Lambda@Edge — cheaper and lower-latency, and modern CloudFront Functions support HMAC-SHA256 verification via the built-in crypto module) checks every request for a valid signed session cookie before it ever reaches S3. No cookie, or an invalid one, redirects to /login.html — the one path deliberately exempted from the check.

A second CloudFront behavior (/auth/*, uncached, so Set-Cookie responses reach the browser same-origin) routes to an API Gateway HTTP API backed by several Lambdas, including:

  • Request code — checks the submitted email against an allowlist (DynamoDB — exact addresses or domain suffixes), generates a 6-digit OTP, stores only its hash with a short expiry, and emails it via Resend. Returns the same generic response whether or not the email is actually allowlisted, to avoid leaking who's on the list.
  • Verify code — checks the submitted code against the stored hash, enforces a max-attempts lockout, and on success issues an HttpOnly; Secure; SameSite=Lax session cookie (14-day expiry) signed with an HMAC secret shared between the Lambdas and the CloudFront Function via a CloudFront KeyValueStore.
  • Admin allowlist — a small /admin.html page (linked nowhere public) lets an admin session list/add/remove allowlist entries, and can also generate a short-lived, time-boxed magic link as a login fallback for anyone whose email doesn't arrive for reasons outside this site's control. Authorization comes entirely from an admin claim baked into the signed session token at login time — re-checked server-side on every request, never trusted from the client.

Login email was originally sent via Amazon SES, which turned out to be the wrong tool for a low-volume personal project: SES's sandbox mode requires every recipient to individually verify their address before they can receive mail, and two separate production-access requests (each with a detailed, specific use-case description) were denied with the same boilerplate response and no actionable reason given either time. That pattern is consistent with automated risk-scoring on account age and history rather than a human evaluating the actual request — not something a better-written appeal was likely to change. Rather than keep working around it, the send path was migrated to Resend, a transactional-email API that only requires the sending domain to be verified (DKIM/SPF/DMARC — the same category of DNS setup SES also needed), not each individual recipient. The migration touched one Lambda and a handful of DNS records; the rest of the OTP flow above is unchanged.

CI/CD Pipeline (GitHub Actions)

No Long-Lived AWS Keys

The pipeline uses GitHub OIDC federation to assume an AWS IAM role — there are no AWS access keys stored as GitHub secrets. On each push to main, GitHub presents a short-lived OIDC token; AWS STS validates it and issues temporary credentials scoped to exactly the permissions needed for deployment.

This is a meaningful DevSecOps detail: credential rotation is automatic, blast radius is limited, and there are no static secrets to leak or rotate.

Deploy Workflow (deploy.yml)

  1. Check out code.
  2. Install Node dependencies for the CDK app (infra/).
  3. Assume the deployment IAM role via OIDC (aws-actions/configure-aws-credentials).
  4. Run cdk deploy --require-approval never to provision/update infrastructure.
  5. Sync site files to S3 (aws s3 sync) with appropriate cache-control headers.
  6. Create a CloudFront invalidation for /* so updated HTML is served immediately.

PR Infrastructure Diff (cdk-diff.yml)

On pull requests that touch infra/**, a separate workflow runs cdk diff and posts the output as a PR comment. Infrastructure changes are visible in review before merge — a small but meaningful guardrail that mirrors enterprise change-management practices.

Content Architecture: Data-Driven Résumé

Résumé content lives in site/content.json — a structured JSON file separate from the HTML template and rendering logic. Updating the résumé means editing the JSON, not touching HTML. The renderer (site/build.js) reads the JSON at page load and populates the DOM.

This "content as data" separation mirrors the golden-path / platform-template pattern central to developer experience work: the what (content) is decoupled from the how (template), so authors don't need to understand the rendering layer to update content.

DevSecOps CI Hardening

The pipeline described above also carries four concrete DevSecOps controls, all enforced automatically on every push/PR rather than relying on a manual review step:

  • CodeQL static analysis (SAST) — scans infra/** TypeScript and site/** JavaScript on every push to main, every PR, and a weekly schedule.
  • Dependabot — weekly automated PRs for outdated npm packages (infra/, with AWS SDK/CDK packages grouped to reduce noise) and GitHub Actions versions.
  • Gated npm audit — a required CI step in both cdk-diff.yml and deploy.yml that fails the build on newly introduced vulnerabilities above a configured severity threshold.
  • ESLint — also gated in both workflows, catching real correctness issues (e.g. dead code) before they reach main.

These badges are GitHub's own live status images — they aren't screenshots, they update automatically as the workflows run. See the Security Scorecard for a working artifact built the same way as the DORA metrics page: a scheduled job pulls this repo's own CodeQL alert counts, Dependabot PR activity, and current npm audit findings and renders them live.

AI Assistant Applet

Every page carries a small floating Ask AI button — a page-aware assistant that answers questions grounded in this site's own published data (the résumé, DORA metrics, security scorecard, and 100-day plan JSON). It knows which page you're on and says so; try it.

Deliberately no Bedrock Agent or Knowledge Base: this site's entire public data surface is well under 100KB, trivially small relative to any modern model's context window, so a vector store would add real always-on cost (OpenSearch Serverless has a nontrivial always-on minimum) for zero benefit. Instead, a Lambda calls the Bedrock Runtime Converse API directly — Claude Haiku via its cross-region inference profile — with a system prompt built fresh each request from the site's own JSON files.

The applet sits behind the same OTP session gate as the rest of the site, with its own layers of defense specific to a public chat surface: a Bedrock Guardrail (content filters including prompt-attack detection, since page context rides along in every prompt; PII anonymization for phone/SSN/address — deliberately not name or email, since answering with Raymond's own name and contact address is the entire point), a dedicated least-privilege IAM role separate from every other role in this stack, a combined rate-limit-and-message-cap enforced atomically in DynamoDB, and a runtime kill switch that disables it instantly without a redeploy. The full conversation is sent with every request (not just the newest message) so the assistant has real memory across turns and survives a page refresh.

AI-Assisted Build Process

What Was AI-Assisted

  • Initial scaffolding — project structure, CDK stack skeleton, GitHub Actions workflow YAML, and this prose were drafted with Claude (Anthropic) as a co-author, guided by specific prompts describing the architecture requirements.
  • CSS design system — the custom-property-based stylesheet was drafted by the AI and reviewed/adjusted for accessibility (contrast ratios, focus styles, responsive breakpoints).
  • IAM policy scoping — the AI drafted least-privilege IAM policy statements; each was reviewed against AWS documentation before use.

What Was Human-Reviewed and Edited

  • All résumé content — sourced directly from the source résumé document. No AI-generated claims about experience, titles, dates, or metrics.
  • Security choices — OIDC over static keys, OAC over public bucket, block-public-access settings — each was a deliberate decision, not an AI default.
  • CDK construct selection — e.g., choosing aws_cloudfront.Distribution with OAC over the legacy CloudFrontWebDistribution.
  • This write-up — drafted with AI assistance, then read and edited by hand for accuracy and tone.

The Broader Point

AI assistance accelerated the initial scaffolding significantly — the kind of work that normally takes an hour of copy-pasting boilerplate took minutes. The value was in moving quickly from "blank repo" to "working skeleton" so human judgment could be applied to the parts that matter: content accuracy, security posture, and architectural decisions. That is exactly the model the DevEx role is meant to enable at scale.

Estimated AWS Cost

At résumé-traffic volumes (tens to low hundreds of requests/month), every piece of this stack is designed to stay near-zero cost, not just the original S3 + CloudFront layer:

  • S3: effectively $0.00 (well under 1 GB storage, negligible GET requests via CloudFront).
  • CloudFront: 1 TB free transfer/month on the free tier; well under that.
  • Route 53: ~$0.50/month hosted zone, plus the domain's annual registration cost amortized.
  • OTP gate (Lambda, API Gateway, DynamoDB, Resend): effectively $0.00 at this request volume — all pay-per-request or free-tier, well under Resend's free-tier send limit.
  • AI assistant applet (Bedrock Haiku, plus the same Lambda/API Gateway/DynamoDB pattern): realistically ~$1-2/month even with regular interview-time usage, well under a $20/month ceiling set for the feature.
  • Total: under $1.50/month in steady state, watched by an AWS Budgets alarm (whole-account, $10/month threshold, forecasted and actual notifications) — a concrete, live demo of cost awareness rather than just a claim.

Custom Domain

The site is served at resume.pages-enterprise.com, not a bare *.cloudfront.net URL — entirely provisioned by CDK, no manual console steps:

  • A public ACM certificate in us-east-1 (required for CloudFront), DNS-validated rather than email-validated, referencing the pre-existing hosted zone by fixed attributes (not fromLookup) so cdk synth doesn't need account/region context.
  • Route 53 alias A/AAAA records pointing the subdomain at the CloudFront distribution.
  • Resend verified at the domain level against a dedicated subdomain, send.pages-enterprise.com — DKIM/SPF/DMARC records provisioned directly via the AWS CLI against the same Route 53 hosted zone, kept separate from any of the zone's other records so nothing collides.
